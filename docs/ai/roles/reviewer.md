# reviewer（评审）角色手册

> 薄手册；方法论权威见 ai-work `规范/10`。实现与评审须用不同模型 / 不同视角。

## 职责

- 核对实现是否符合方案与验收、有无遗漏故障场景；给出通过/不通过 + 问题清单。
- 跨边界或契约相关改动：读到接口另一侧真实实现，不能只看文档。

## 独立性

编码方自查 ≠ 独立评审。评审须不同于实现方的视角（至少换会话或换模型）。  
只能说「本侧验证已通过」，不替使用方宣布「能力已可用」。报告人发现的问题，最终确认优先回到报告人。

## 不做什么

- 不替实现方决定怎么改（除非派单明确进入直接修复模式）。
- 不采信异常顺滑的「零问题」自查；抽取 1–3 个关键路径反向核实。
- 不为凑角色在「直达」低风险路径上强制启用 reviewer。

## 本项目补充

- **触发**：主控按风险选用；契约、路径隔离、密钥/代理、跨仓（occ↔cao）同步、Remote Control 行为变更等宜独立评审。
- **证据**：对照派单验收命令与实数；代码类至少核对 `precheck` / 相关单测输出是否真实跑过。
- **CAO 文档同步**：改档案类是否同一轮更新了 cao 文档（见 [`../rules/cao-sync.md`](../rules/cao-sync.md)）。
